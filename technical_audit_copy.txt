Read-only technical audit of the current project

This audit is based on the actual code in the workspace, not assumptions. I did not modify any files.

1) Project structure audit

Framework and version
- Framework: Next.js 15.4.9
- UI library: React 19.2.1
- Language: TypeScript 5.9.3
- Styling: Tailwind CSS v4
- App router: Yes, using the app/ directory
- Runtime: Node server-side capability with Next.js server route and server-side fetches

Evidence:
- package.json
- next.config.ts
- tsconfig.json

Frontend architecture
- Client UI is in app/page.tsx
- Results are rendered with reusable cards from components/AnalysisCards.tsx
- Local scan history is stored in browser localStorage
- No centralized state management library, no Redux/Zustand, no auth flow

Backend / API architecture
- API entrypoint is app/api/analysis/route.ts
- It accepts POST JSON with { url }, validates the input, normalizes it, resolves protocol, then calls analyzeUrl
- Response shape is simple JSON: { success, message, data }

Main analysis pipeline
Actual flow in code:
1. User submits URL from app/page.tsx
2. API route validates and normalizes URL in app/api/analysis/route.ts
3. resolveProtocol probes HTTPS/HTTP in utils/url.ts
4. analyzeUrl orchestrates the scan in lib/analyzer.ts
5. It fetches page HTML and concurrently runs website metadata, IP geolocation, WHOIS, DNS, SSL, HTTP headers, cookies, redirects, links, emails, phones, ports, sitemap
6. It calculates a risk score with lib/scoring.ts
7. It returns a JSON report to the frontend

Service/module structure
Relevant modules:
- lib/analyzer.ts — orchestration
- lib/website.ts — title/favicon/domain
- lib/ipinfo.ts — IP and geolocation
- lib/whois.ts — WHOIS lookup
- lib/dns.ts — DNS record resolution
- lib/ssl.ts — TLS certificate interrogation
- lib/headers.ts — HTTP headers
- lib/cookies.ts — cookie extraction
- lib/redirects.ts — redirect chain tracing
- lib/links.ts — internal/external link parsing
- lib/emails.ts — email extraction
- lib/phones.ts — phone extraction
- lib/ports.ts — common port probe
- lib/sitemap.ts — robots/sitemap detection
- lib/urlIntelligence.ts — entropy/Unicode/homograph helpers
- lib/urlAnalysis.ts — standalone legacy heuristic analytics
- lib/engine/RiskEngine.ts — risk scoring engine
- lib/rules — rule evaluators

Rule Engine architecture
- Rule metadata is defined in types/rules.ts
- Core engine is lib/engine/RiskEngine.ts
- Rule categories include URL, SSL, WHOIS, DNS, Headers, Cookies, Redirects, Website
- Each rule has id, title, description, recommendation, category, severity, weight, triggered
- Final score is capped at 100 and verdict is based on thresholds:
  - phishing if score >= 60
  - suspicious if score >= 25
  - safe otherwise

Threat Intelligence architecture

- The project uses heuristic analysis and public metadata fetches, not live TI feeds
- The package includes @google/genai, but there is no actual Gemini-based scan path in the source code

4) Performance audit

Current execution pattern
- The scan uses Promise.all() in lib/analyzer.ts, which is good for concurrency
- But there are multiple fetches to the same target in parallel:
  - HTML fetch
  - headers
  - cookies
  - redirects
  - sitemap checks
  - website content parse
- Some modules also trigger network probes:
  - common port scan in lib/ports.ts
  - WHOIS API request
  - IP API request
  - direct TLS handshake

Timeouts and retry behavior
Observed:
- HTML fetch uses AbortSignal.timeout(5000)
- resolveProtocol uses 4000ms timeout
- SSL handshake uses 5000ms timeout
- redirect chain has no timeout
- headers and cookies fetches have no timeout
- WHOIS request has no timeout
- IP geolocation request has no timeout
- port probes use 1500ms timeout per port

Retry behavior
- No retry logic
- No exponential backoff
- No circuit breaker
- A single slow dependency can stall the full scan

Caching
- No cache layer
- No request memoization
- No TTL
- No provider response cache

Duplicate requests
Yes:
- same target URL is fetched repeatedly for HTML, redirect checks, header checks, cookie checks, sitemap checks
- a page may be fetched 4–6 times in a single scan

Maximum scan time
Likely highly variable, but the architecture can easily push into 10–30 seconds on slow or hostile endpoints because of:
- multiple remote fetches
- TLS handshake
- redirect chain loop
- port scanning
- WHOIS request
- IP API request

Potential bottlenecks
- lib/ports.ts: network scanning of common ports is a major bottleneck and the most invasive
- lib/redirects.ts: redirect loops can multiply the wait time
- lib/whois.ts: third-party WHOIS API latency
- lib/ipinfo.ts: external IP API latency
- lib/analyzer.ts: large number of simultaneous outbound requests

Serverless compatibility
- Next.js standalone output helps, but several practices are poor for serverless:
  - raw arbitrary outbound network calls
  - port scanning
  - direct TLS to arbitrary hosts
  - lack of egress control
  - no concurrency controls
- This is not ideal inside constrained serverless environments

5) Security audit

1. SSRF and arbitrary outbound requests
Severity: Critical
Issue:
- Server code sends requests to user-controlled URLs without allowlisting
- fetch() is called on arbitrary supplied hostnames
- redirects.ts follows redirect targets from a user-controlled URL
- resolveProtocol reaches the target with a HEAD request before analysis

Recommended fix:
- block private, loopback, link-local, and documentation IP ranges
- restrict outbound destinations to allowlisted domains or safe fetch policies
- avoid following redirects to non-public destinations

2. Internal/private IP and localhost access
Severity: Critical
Issue:
- utils/url.ts explicitly accepts localhost, 127.0.0.1, 192.168.*, 10.*, and private RFC1918 ranges
- This is dangerous in server-side scanning because internal services can be targeted

Recommended fix:
- deny private/loopback/link-local and metadata addresses by default
- add IP classification layer before fetching

3. Cloud metadata access
Severity: High
Issue:
- no filtering for 169.254.169.254, metadata.google.internal, link-local IP ranges, or IPv6 local addresses
- user-controlled hostnames may resolve into internal or cloud metadata services

Recommended fix:
- explicitly block metadata and link-local namespaces
- add host/IP denylist before outbound fetches

4. Redirect abuse
Severity: High
Issue:
- redirect chain follows user-controlled URLs without validation
- malicious target may redirect to internal or sensitive endpoints
- redirect: 'manual' is still fetching and following remote targets without trust enforcement

Recommended fix:
- validate each redirect target against a trust/allowlist model
- refuse redirect chains crossing blocklisted or private networks

5. Extremely large responses
Severity: High
Issue:
- lib/analyzer.ts fetches page HTML with res.text() and stores it in memory without a size cap
- a malicious site can return huge payloads and exhaust memory or CPU

Recommended fix:
- impose maximum response size
- abort on excessive body length
- set strict timeouts and memory ceilings

6. Malicious HTML content
Severity: Medium
Issue:
- HTML is analyzed via regexes and string inspection, not sanitized
- the app does not render raw user HTML, but it does process hostile content in Node
- regex extraction may be abused with crafted large HTML payloads

Recommended fix:
- cap HTML content length
- parse with a safe, bounded parser
- avoid unnecessary processing on huge or malformed HTML

7. Denial-of-service via network probing
Severity: Critical
Issue:
- lib/ports.ts opens multiple sockets to the target host
- aggressive scan patterns can be abused to turn the backend into a port scanner
- can affect the target and consume server resources

Recommended fix:
- remove or gate port scanning behind admin-only controls
- reduce the list and increase protections
- disable from public routes

8. Missing rate limiting
Severity: High
Issue:
- no throttling or rate limiting in app/api/analysis/route.ts
- one user can hammer the server with many outbound scan jobs

Recommended fix:
- enforce request quotas per IP
- queue or background processing for heavy analysis

9. Input validation gaps
Severity: Medium
Issue:
- only checks that the field is a string and calls normalizeUrl
- no explicit host validation, no domain policy, no anti-abuse checks

Recommended fix:
- validate hostname and scheme strictly
- reject dangerous domains and internal ranges

10. Unsafe external requests over HTTP
Severity: Medium
Issue:
- lib/ipinfo.ts uses http://ip-api.com/json/${ip}
- encrypted transport is not used for this lookup
- data is exposed in transit

Recommended fix:
- use HTTPS-only API endpoints
- consider dedicated, authenticated providers for production

11. API key exposure risk
Severity: Low
Issue:
- no production secret use in the source, but project includes a Gemini-related template in .env.example and package references
- no actual runtime secret usage in the scan logic

Recommended fix:
- keep secrets only in hosting env and never in repo
- remove unused dependencies and stale env references

12. User-controlled URL handling
Severity: Critical
Issue:
- every filter and fetch is based on user-provided URLs
- code does not implement a safe, minimal trust model

Recommended fix:
- enforce secure fetch policies
- redact and isolate any outbound network access from public requests
